## 2. 每个核心文件或模块的作用猜测

### 顶层核心

- `main.cpp`
  - 超大总控脚本式入口
  - 负责全局对象创建、设备初始化、线程启动、场景函数、键盘交互、状态切换、仿真同步
- `robot.cpp` / `robot.h`
  - 核心控制状态机
  - 内含轨迹执行、动力学调用、关节电机映射、零位处理、动作模式切换
- `dynamics.cpp` / `dynamics.h`
  - 基于 RBDL 的模型加载、正逆运动学、逆动力学接口
- `motionplanning.cpp` / `motionplanning.h`
  - 基于 Reflexxes 的轨迹规划包装层

### 设备与执行层

- `mitmotor.*`
  - MIT 电机 CAN 打包、解包、状态读取、保护逻辑
- `magneticencoder.*`
  - 磁编码器 CAN 数据解包与零位处理
- `rtcan.*`
  - CAN 口初始化、发送、接收任务封装
- `rt485.*`
  - 485 通信封装，用于 Dynamixel
- `Dynamixel.*`
  - 夹爪或外设电机控制封装
- `ftsensor.*`
  - UDP 力传感器通信与简单力控逻辑
- `t265camera.*`
  - RealSense T265 姿态采集封装
- `Hololens.*`
  - HoloLens UDP 消息接收、姿态变换、动作触发
- `CPython.*`
  - 通过 socket 与 Python 侧做简单通信

### 仿真桥接

- `vrepsim.*`
  - 与 V-REP / CoppeliaSim 交互
- `mujocosim.*`
  - MuJoCo 场景加载、控制回调、渲染窗口

### 历史与备用

- `kinematics.*`
  - 与 `coppeliaKinematicsRoutines` 搭配的旧运动学接口
  - 当前构建中未直接启用
- `sensor.*`、`motor.*`
  - 明显不完整，像历史残留或早期试验文件
- `vrepsimb0.*`
  - 旧版仿真接口尝试
- `main_back1.txt`、`main.cpp.YezWNd`
  - 历史备份或临时文件

## 3. 项目的主要入口文件有哪些

### 直接入口

- `main.cpp`
  - 真实程序入口
  - `int main()` 在文件尾部

### 构建入口

- `hitExoLimb-R3.pro`
  - qmake 工程描述
- `Makefile`
  - 由 qmake 生成的 Linux 构建文件

### 运行时重要入口函数

- `init(bool vrepEnable, const char* vrepIP)`
  - 初始化 V-REP、CAN、485、RBDL、机械臂对象、HoloLens、MuJoCo
- `robotArm::startCtrl(...)`
  - 启动控制任务
- `robotArm::ctrlStateMachine()`
  - 实际控制主循环
- `TopCtrl(...)`
  - 顶层数据与力控处理
- `keyscan()`
  - 命令输入和动作触发
- `state_change()`
  - 支撑状态自动切换
- `processt265()`
  - T265 数据处理线程

## 4. 配置文件有哪些

### 明面上的配置文件

- `hitExoLimb-R3.pro`
  - 源文件、头文件、包含路径、链接库
- `Makefile`
  - Linux 构建细节

### 模型与资源文件

- `ikmodel/*.ik`

### 伪配置

原项目大量配置没有单独放进配置文件，而是直接硬编码在源码里，例如：

- `/home/.../HitLimb_up.urdf`
- `/dev/ttyUSB0`、`/dev/ttyUSB1`
- `192.168.1.101`
- 传感器初始角度
- 力控阈值、速度阈值、时间步长

这说明原项目“配置与代码强耦合”问题明显。

## 5. 数据流与调用链大致走向

### 启动阶段

1. `main()` 调 `init(true, "192.168.1.101")`
2. `init()` 连接 V-REP
3. 初始化 CAN、485、RBDL、机械臂、HoloLens、MuJoCo
4. 为左右机械臂启动实时控制任务
5. `main()` 再起 `keyscan`、`processt265`、`state_change`、`TopCtrl`

### 控制阶段

1. 用户命令或状态线程触发动作
2. `robotArm::beginMotion()` 修改状态机动作标志
3. `robotArm::ctrlStateMachine()` 根据 `motiontype` 进入对应分支
4. `motionplanning` 生成下一步轨迹点
5. `dynamics` 计算关节/末端关系与力矩
6. `jointToMotor()` 把关节命令变成电机命令
7. `sendMotorCmds()` 下发到 CAN / 485 设备
8. `fetchMotorStates()` 与编码器数据回读后再更新到关节侧
9. `main.cpp` 把当前姿态同步到 MuJoCo / V-REP

## 7. 命名混乱、职责不清、注释缺失最严重的地方

### `main.cpp`

- 文件过大，混合了初始化、场景逻辑、状态逻辑、仿真同步、键盘处理
- 全局变量极多
- 变量命名短且上下文依赖强，例如 `a`、`b`、`ids`、`cmd`
- 很多函数名只能靠业务背景猜测

### `robot.h`

- 单个类 `robotArm` 承载了大量结构体和成员
- 结构体命名风格不统一
- 同一类中同时出现控制状态、滤波状态、轨迹点、保护参数、业务动作状态

### `robot.cpp`

- `ctrlStateMachine()` 过长，职责极重
- 内部混杂动作模式切换、轨迹执行、动力学调用、采样记录、硬件访问
- 依赖 `extern` 全局变量

### `Hololens.cpp`

- 文本处理、坐标变换、网络通信、动作触发耦合在一起
- 注释存在编码问题，阅读成本高

## 8. 哪些地方适合拆分，哪些地方适合保留原结构

### 适合拆分

- `main.cpp`
  - 应拆成“应用启动”“场景脚本”“状态管理”“输入处理”“仿真同步”
- `robotArm`
  - 应拆成“控制器骨架”“轨迹运行时状态”“关节电机映射”“硬件执行接口”
- `Hololens.*`
  - 应拆成“网络协议”“位姿变换”“动作触发器”

### 适合先保留原结构

- `dynamics.*`
  - 原本已经是相对清晰的算法接口层
- `motionplanning.*`
  - 原本就是较小包装层
- `mitmotor.*`
  - 尽管有魔法数字，但职责比较集中
- `magneticencoder.*`
  - 单一职责比较明确

## 9. 风险检查

### 隐式依赖

- 存在
- `robot.cpp` 使用了多个 `extern` 全局变量，直接依赖 `main.cpp`

### 相对路径陷阱

- 存在
- `./Rsras1.xml`
- `../../SRL2/dynamixel_sdk/...`
- 若干绝对路径 `/home/...`

### 魔法数字

- 大量存在
- 例：减速比、阈值、角度限制、控制周期、IP、串口、初始角度

### 全局变量滥用

- 明显存在
- `main.cpp` 顶层全局状态非常多

### 循环导入

- 没看到明显硬死循环
- 但头文件耦合较高，很多地方靠前向声明撑住

### 脚本式写法过重

- 明显存在
- 主要集中在 `main.cpp`

### 配置与代码强耦合

- 明显存在
- 路径、设备号、IP、控制周期等都硬编码在源码中

## 10. 对学习版迁移的结论

### 当前最适合优先迁移的最小链路

- `jointToMotor` / `motorToJoint`
- `calcPVAfromP`
- `Filter`
- `motionplanning` 的接口骨架
- `dynamics` 的接口骨架
- 一个不连真实硬件的离线主流程

### 当前不适合一开始就迁移为“可运行等价版”的模块

- Xenomai 实时任务
- PCAN / 485 通信
- RealSense T265
- FT 力传感器
- HoloLens 联动
- MuJoCo / V-REP 真联动

这些模块都应先做：

1. 映射
2. 说明
3. 待确认标记
4. 最后才做替身化或等价迁移
